# Curve balls

A **curve ball** is a named, seeded, deterministic change of a model that *matters*. The benchmark
hands an agent a model in which something has been changed; the agent's answer is scored against
the reference solution of the changed model and, for a diagnosis task, against the **change
record**. Code: `benchfea.bench.curveballs`; command line: `benchfea perturb`.

> This file is generated by `tools/build_curveball_docs.py`. Every number in it comes from running
> the code on generated models; the prose of each curve ball is the text of its registration.
> Nothing here says that a result has been reviewed or approved by anyone: "verified" in this
> project means only *passed the tiers listed, at the tolerances stated* (docs/VERIFICATION.md), and
> the verification route given for each example is an **expectation**, not a result.

```python
from benchfea.bench import generate, curveballs

base = generate("portal_frame", seed=1, difficulty=1).document
p = curveballs.apply(base, "support_fixed_to_pinned", seed=0)   # Perturbed(document, record)
p.document                     # the changed input document
p.record.changes               # [Change(op, path, before, after, index)] -- JSON pointers
p.record.entities              # {"nodes": [...], "supports": [...]} ids touched
p.record.effect_class          # "changes-analysis"
p.record.effect                # measured: analysisChange, designRatioChange, where, before / after
p.record.apply(base)  == p.document      # the record IS the difference
p.record.revert(p.document) == base
curveballs.apply(base, "offset_removed", seed=0)                # raises NotApplicable(reason)
```

```
benchfea perturb --list
benchfea perturb model.json release_added --seed 3 -o variant.json --record variant.record.json
benchfea perturb model.json support_removed --show-record
benchfea perturb model.json --applicable           # which curve balls fit this model
```

Exit codes of `benchfea perturb`: 0 applied; 7 not applicable (the reason is printed); 2 usage,
unknown curve ball or unreadable model.

## 1. How a curve ball is applied

1. The base model is analysed (strict: all invariants passed, every iteration converged) and
   designed. A base model that is not analysable is refused.
2. The curve ball lists its **candidate targets** in the base model (member ends, supports, loads,
   design blocks, ...). No candidate: `NotApplicable`, naming the precondition that is not met.
3. The candidates are put in a seeded order: SHA-256 of
   `"benchfea.bench|curveball|<version>|<name>|<seed>"` -> PCG64, Fisher-Yates on the raw integer
   stream (the same construction as the generators; never Python's `hash()`). Candidates that keep
   the model inside what the cross-check is expected to follow (`bench.tier_c_expected`) are tried
   before candidates that take a cross-checkable model outside it.
4. Candidate by candidate (at most `MAX_CANDIDATES` = 12) the perturbed model is
   analysed and designed and **the effect is measured** against the base model. The first candidate
   whose effect class is one the curve ball declares and whose effect is material is taken. Every
   candidate dropped on the way is listed in the record (`rejected`, with the measured values).
5. No candidate passes: `NotApplicable`, listing what was tried and what was measured.

A perturbed model that the engine refuses for any reason other than a plain mechanism or a
validation error (beyond the elastic critical load, not converged, an invariant failed, a
mechanism that exists only through slack tension-only members, an ill-conditioned matrix) has no
reference solution; such a candidate is never accepted.

## 2. Effect classes and materiality

| effect class | what happened | material when | reference solution of the perturbed model |
|---|---|---|---|
| `changes-analysis` | the analysis results changed | **analysis change ≥ 5%**, or a design member changes between pass / conditional and fail; for the curve balls that change the *resistance* of a member (its section or orientation) also: the governing **design ratio of a design member changes by ≥ 5%** | results (and design) of the perturbed model |
| `design-only` | the analysis is **bitwise identical** (every array of every combination), the design changed | governing design ratio of a design member changes by ≥ 5%, or a design member changes pass / fail | the same results; the design of the perturbed model |
| `creates-mechanism` | the base model is analysed, the perturbed one is refused with `stability.mechanism` | always | the solver's structured **mechanism diagnosis** (`reference.diagnosis` in the record) |
| `invalid-model` | the base model is valid, the perturbed one is refused by validation | always | the validator's list of problems (`reference.problems`) |

**Analysis change** (`effect.analysisChange`), measured in physical units (N, mm) on the nodes and
members both models have, for every combination: the largest difference, entity by entity, of

* the nodal translations and the peak displacement of each member axis, divided by the largest
  such displacement of the base model in that combination;
* the reaction forces and member forces (end forces as global vectors, peak axial force and peak
  resultant shear along each member), divided by the largest such force of the base model in that
  combination;
* the reaction moments and member moments (end moments as global vectors, peak torque and peak
  resultant bending moment along each member), divided by the largest such moment of the base model
  in that combination;

and the largest of these over the combinations. The difference is taken where it occurs, so a load
path that moves is measured even if the peak values stay the same; it is normalised by the governing
(peak) value of its kind, so a large relative change of a negligible quantity does not count; member
quantities are global vectors or resultants, so turning a member's local axes is not by itself a
change.
`effect.analysisChangeAt` names the quantity, the node or member and the combination.

**Design ratio change** (`effect.designRatioChange`): largest relative change of the governing
ratio of a design member (`effect.designRatioChangeAt` names it and its limit states).

Which criteria count for a curve ball is listed with it ("Material through"). A curve ball that
changes only the demands (loads, supports, releases, offsets, constraints, units) is not made
material by a design ratio alone: with the resistance unchanged a ratio moves with the member
forces, and a ratio that jumps while no governing force moves by 5% would be a discontinuity of the
design checks, not an effect of the change. `second_order_off` counts the analysis change only: it
is applicable only where switching the second-order analysis off moves the analysis results by at
least 5%.

The thresholds are `curveballs.THRESHOLDS`; they are the same for every curve ball and model, and a
target that misses them is dropped -- never forced.

## 3. The change record

`record.to_dict()` (format `benchfea-curveball-record` 1.0.0; `benchfea perturb --record FILE`):

| field | content |
|---|---|
| `curveBall`, `seed`, `category`, `title`, `curveBallVersion` | which curve ball, applied with which seed |
| `effectClass` | the measured class (one of those the curve ball declares) |
| `target` | one line naming what was chosen |
| `changes` | the exact difference of the two documents: `{"op": "replace" \| "add" \| "remove", "path": JSON pointer, "before", "after", "index"}`. `index` is the position of an added / removed key in its object, so that key order is reproduced. Arrays whose length changes are replaced as a whole |
| `entities` | ids touched, by kind (`members`, `nodes`, `supports`, `constraints`, `sections`, `loadCases`, `combinations`, `designMembers`, `units`) |
| `whyItMatters` | the physical reason, in plain language |
| `precondition` | what the base model must have |
| `effect` | the measured effect: `class`, `criterion`, `thresholds`, `analysisIdentical`, `analysisChange`, `analysisChangeAt`, `analysisChangeByCombination`, `designRatioChange`, `designRatioChangeAt`, `designPassFailChanged`, `designStatusChanges`, `base` / `perturbed` summaries in file units, and facts of the curve ball (factor applied, amplification, ...) |
| `reference` | `kind`: `results` \| `diagnosis` \| `validation-problems`; for a mechanism the full diagnosis, for an invalid model the problems |
| `verification` | expected verification route of the perturbed model |
| `rejected` | candidates measured and dropped before the accepted one |
| `baseHash`, `perturbedHash` | SHA-256 of the two documents |

The change list is not written by the curve balls: it is the structural difference of the base and
the perturbed document (`curveballs.diff`). `record.apply(base)` and `record.revert(perturbed)`
check every `before` value while applying; the tests (and this script, on every run) require both
to reproduce the other document exactly, key order included. A diagnosis answer can therefore be
matched against `changes[*].path` and `entities`.

## 4. Verification route

Curve balls prefer targets that keep the perturbed model verifiable. Where that is not possible the
record says so (`verification.route`, `verification.notes`):

* `changes-analysis` / `design-only`: `benchfea verify` on the perturbed model. If the perturbed
  model uses a feature that fewer than two independent solvers can represent (for example rigid end
  offsets together with second-order combinations), tier C cannot pass and the pipeline quarantines
  the reference; a quarantined reference is not published.
* `creates-mechanism`: the diagnosis tiers of docs/VERIFICATION.md section 4.
* `invalid-model`: there is nothing to analyse; the reference answer is the validator's problem
  list, reproducible with `benchfea validate`.

The route in a record is derived from the features of the perturbed model; it is not the outcome of
a verification run. Two cases in which the expectation is negative, both measured on the examples
below and reported there as quarantined:

* **A loaded node without members.** Removing a diaphragm (or detaching its master) leaves the
  master node, which carries the storey loads, connected to nothing. The engine refuses the model
  as a mechanism (mode kind `node`, cause `no-stiffness`: the node is loaded in DOFs where it has
  no stiffness). The diagnosis tiers do not confirm it: the independently assembled stiffness of
  tier N leaves memberless nodes out, finds no zero-stiffness motion, and so disagrees with the
  number of mechanisms; tiers K and C follow. The reference of such a perturbed model is
  quarantined (category `disagreement`). The record says `expectedVerifiable: false`.
* **A node on the axis of a member.** A reversed end offset puts the flexible end beyond its node,
  so the member passes over its own end node. The PyNite translator refuses such a topology (PyNite
  would connect the node to the member), which leaves one foreign solver: tier C is
  `not-representable`. The record's expectation includes this check.

To accept only targets whose reference actually passes, apply with verification:

```python
curveballs.apply(base, "offset_removed", seed=0, verify=True)   # record.verification["run"]
```

```
benchfea perturb model.json offset_removed --require-verified
```

Every candidate that is material is then put through `benchfea.verify.verify_model` (analysis
results or mechanism diagnosis; for a design-only effect, or with `verify="design"`, also the design
results and tier F) and dropped unless the status is `verified`; if none is left the curve ball is
`NotApplicable`. `verified` means only: passed the tiers listed in `record.verification["run"]`, at
the tolerances of docs/VERIFICATION.md. This costs far more than the measurement.

## 6. The curve balls

### Rigid links and diaphragms

#### `constraint_removed` -- rigid link / diaphragm removed

* **Effect class**: `changes-analysis` or `creates-mechanism`
* **Material through**: `analysisChange`, `designPassFailChanged`
* **What it changes**: Deletes one rigid constraint (`/constraints/<id>`).
* **Why it matters**: A rigid diaphragm or link is a kinematic assumption that decides how lateral load is shared: with it the connected nodes move as one rigid body and the load goes to the frames in proportion to their stiffness and position; without it each node moves on its own and the load follows the members. Removing it frees the slaves from the master: storey forces applied at the master no longer reach the frame (a master without members is then a loaded node with no stiffness -- a mechanism), or the floor racks and twists instead of moving rigidly.
* **Result quantities it moves**: Storey drifts and floor rotation, the split of storey shear between frames, column and beam end moments; or no results at all (mechanism at the former master).
* **Applicable when**: the model has at least one rigid constraint (rigidLink or rigidDiaphragm).

Example (actual run, seed 0) on `generate("diaphragm_frame", seed=1, difficulty=3)`; target: constraint floor1.

* Changes recorded:
  * `/constraints/floor1` removed (was `{"type": "rigidDiaphragm", "master": "CM1", "slaves": ["A1.1", "A2 ...`)
* Effect class **creates-mechanism**: the base model is analysed, the perturbed one is refused as a mechanism (2 mechanism(s)). Reference = the diagnosis; first mode: *node CM1 is loaded in ux, ry, where it has no stiffness: no member connects to it* (kind `node`, cause `no-stiffness`).
* Expected verification route: diagnosis tiers N, K, C, E of benchfea.verify (docs/VERIFICATION.md section 4): null space of an independently assembled stiffness, engine matrix, two foreign solvers under a probing load, invariance of the diagnosis; NOT expected to pass: the diagnosis reports a loaded node without any member (cause no-stiffness), and the diagnosis tiers have been measured not to confirm this kind of mechanism (docs/CURVEBALLS.md section 4) -- the pipeline quarantines it.
* Verification run on this perturbed model (`benchfea verify`, mechanism diagnosis): `verified` -- passed tiers N, K, C, E, which are all the tiers that apply (meaning and tolerances: docs/VERIFICATION.md).

#### `constraint_added` -- rigid link / diaphragm added

* **Effect class**: `changes-analysis`
* **Material through**: `analysisChange`, `designPassFailChanged`
* **What it changes**: Adds a rigid constraint that the structure does not have: a rigid diaphragm over the nodes of one level, or a rigid link between the two end nodes of a member (`/constraints/<new id>`).
* **Why it matters**: A rigid constraint removes deformation the real structure has. A diaphragm that is not there forces all nodes of a level to translate and twist together, so flexible frames are propped by stiff ones; a rigid link across a member makes that member infinitely stiff, so it attracts load and stops deforming.
* **Result quantities it moves**: Drifts (smaller), distribution of lateral load between frames, forces in the member bridged by a link (its deformation vanishes), reactions.
* **Applicable when**: a level with at least two nodes that are not supported in the DOFs a diaphragm ties and are not part of a constraint, or a frame member whose end node is unsupported and unconstrained (plane frames modelled with out-of-plane supports at every node do not qualify).

* Analysis change (largest, relative to the base peak of its kind): **9.2 %** -- member displacement at `BYA1.1`, combination `SLS1`.
* Combination `SLS1`, before -> after: largest displacement of a member axis 0.5021 in -> 0.4725 in; largest reaction force 20.07 kip -> 20.07 kip; largest member bending moment 357.2 kip·in -> 357.2 kip·in.
* Design: status conditional -> conditional; largest ratio 0.792 (`BYA1.1`) -> 0.741 (`BYB1.1`); largest change of a governing ratio: design member `BYA1.2` 0.0866 -> 0.0191 (77.9 %).
* Materiality criterion met: `analysisChange`.
* Expected verification route: benchfea verify: every applicable tier; tier C (two independent solvers) is expected to be able to follow the perturbed model.
* Verification run on this perturbed model (`benchfea verify`, analysis results): `verified` -- passed tiers C, D, E, which are all the tiers that apply (meaning and tolerances: docs/VERIFICATION.md).

#### `constraint_slaves_dropped` -- constraint attached to too few nodes

* **Effect class**: `changes-analysis`
* **Material through**: `analysisChange`, `designPassFailChanged`
* **What it changes**: Shortens the slave list of a rigid constraint (`/constraints/<id>/slaves`): one slave left out, half of them, or all but one.
* **Why it matters**: A rigid diaphragm or link is a kinematic assumption that decides how lateral load is shared: with it the connected nodes move as one rigid body and the load goes to the frames in proportion to their stiffness and position; without it each node moves on its own and the load follows the members. A node left out of the list is no longer carried by the diaphragm: the master's load enters the structure only through the remaining slaves and has to travel through the members to reach the frames that were disconnected.
* **Result quantities it moves**: Split of storey shear between frames, floor rotation, axial forces in the beams that now act as collectors, drift of the disconnected nodes.
* **Applicable when**: a rigid constraint with at least two slaves.

* Changes recorded:

* Analysis change (largest, relative to the base peak of its kind): **16.9 %** -- member force at `BYB1.1`, combination `ULS3`.
* Combination `ULS3`, before -> after: largest displacement of a member axis 146.8 mm -> 146.8 mm; largest reaction force 123.7 kN -> 123.7 kN; largest member bending moment 7.879e+04 kN·mm -> 7.879e+04 kN·mm.
* Design: status conditional -> fail; largest ratio 0.897 (`BXA1.1`) -> 1.23 (`BYB1.1`); largest change of a governing ratio: design member `BYB1.1` 0.697 -> 1.23 (76.2 %); pass / fail changed for: `BYB1.1`.
* Materiality criterion met: `analysisChange`.
* Expected verification route: benchfea verify: every applicable tier; tier C (two independent solvers) is expected to be able to follow the perturbed model.
* Verification run on this perturbed model (`benchfea verify`, analysis results): `verified` -- passed tiers C, D, E, which are all the tiers that apply (meaning and tolerances: docs/VERIFICATION.md).

#### `constraint_wrong_slave` -- constraint attached to a wrong node

* **Effect class**: `changes-analysis` or `invalid-model`
* **Material through**: `analysisChange`, `designPassFailChanged`
* **What it changes**: Replaces one slave of a rigid constraint by a nearby node that does not belong to it (`/constraints/<id>/slaves/<k>`).
* **Why it matters**: The constraint now ties a node of another part of the structure (typically the node above or below on the same column line) to the master and lets the intended node go. Where that node is supported or already belongs to another constraint the model is contradictory and is refused; otherwise two levels are locked together and the intended node drifts freely.
* **Result quantities it moves**: Either no analysis (validation refuses a slave that is supported in a tied DOF or has two masters), or storey drifts, column shears and moments between the two levels that were locked together.
* **Applicable when**: the model has a rigid constraint and a node outside it.

Example (actual run, seed 0) on `generate("diaphragm_frame", seed=1, difficulty=3)`; target: constraint floor1: slave B1.1 replaced by B2.0.

* Changes recorded:
  * `/constraints/floor1/slaves/2`: `"B1.1"` -> `"B2.0"`
* Effect class **invalid-model**: validation refuses the perturbed model. Reference = the problems: `constraint.slave-restrained` at `/constraints/floor1/slaves/2`.
* Expected verification route: none: the model is refused by validation, there is no analysis to verify (benchfea verify reports 'refused'); the reference answer is the validator's list of problems, reproducible with 'benchfea validate'.
* Verification run on this perturbed model (`benchfea verify`): `refused` -- the engine produces no reference solution for it, as expected for an invalid model.

#### `constraint_wrong_master` -- constraint with the wrong master node

* **Effect class**: `changes-analysis` or `creates-mechanism`
* **Material through**: `analysisChange`, `designPassFailChanged`
* **What it changes**: Changes the master of a rigid constraint (`/constraints/<id>/master`): one of its slaves is made the master (and leaves the slave list), or a nearby node outside the constraint is.
* **Why it matters**: Loads and masses of a floor are applied at the master. If another node is declared master, the node that carries the storey loads is no longer part of the rigid body: a memberless master is left as a loaded node with no stiffness (a mechanism), and a master taken from outside ties the floor to a node that should move independently.
* **Result quantities it moves**: No results (mechanism at the abandoned master, reported by the diagnosis), or drifts and the load path of the storey forces.
* **Applicable when**: the model has a rigid constraint.

Example (actual run, seed 0) on `generate("diaphragm_frame", seed=1, difficulty=3)`; target: constraint floor1: slave B1.1 made master, CM1 detached.

* Changes recorded:
  * `/constraints/floor1/master`: `"CM1"` -> `"B1.1"`
  * `/constraints/floor1/slaves`: `["A1.1", "A2.1", "B1.1", "B2.1", "C1.1", "C2.1"]` -> `["A1.1", "A2.1", "B2.1", "C1.1", "C2.1"]`
* Effect class **creates-mechanism**: the base model is analysed, the perturbed one is refused as a mechanism (2 mechanism(s)). Reference = the diagnosis; first mode: *node CM1 is loaded in ux, ry, where it has no stiffness: no member connects to it* (kind `node`, cause `no-stiffness`).
* Expected verification route: diagnosis tiers N, K, C, E of benchfea.verify (docs/VERIFICATION.md section 4): null space of an independently assembled stiffness, engine matrix, two foreign solvers under a probing load, invariance of the diagnosis; NOT expected to pass: the diagnosis reports a loaded node without any member (cause no-stiffness), and the diagnosis tiers have been measured not to confirm this kind of mechanism (docs/CURVEBALLS.md section 4) -- the pipeline quarantines it.
* Verification run on this perturbed model (`benchfea verify`, mechanism diagnosis): `verified` -- passed tiers N, K, C, E, which are all the tiers that apply (meaning and tolerances: docs/VERIFICATION.md).

#### `constraint_made_flexible` -- rigid constraint replaced by flexible members

* **Effect class**: `changes-analysis`
* **Material through**: `analysisChange`, `designPassFailChanged`
* **What it changes**: Deletes a rigid constraint and adds one frame member of a section of the model from the master to each slave (`/constraints/<id>` removed, `/members/<id>-flex-<k>` added).
* **Why it matters**: Members of finite stiffness do not enforce rigid-body motion: the connected nodes can move relative to each other, so load is shared according to the flexibility of the connecting members instead of the rigid-body rule. Unlike a diaphragm, the stand-in members also couple the out-of-plane DOFs, and they have self weight and are design members like any other.
* **Result quantities it moves**: Floor rotation and drifts, split of storey shear between frames, forces in the columns under the floor; the new members carry forces of their own.
* **Applicable when**: the model has a rigid constraint whose master does not coincide with a slave.

* **Result quantities it moves**: Design ratios of the member (down) and of its neighbours, distribution of moments, deflections and drift (smaller), self weight.
* **Applicable when**: a member for which a heavier section of the same kind exists (in the model or in the generic catalogue of the generators).

#### `sections_swapped` -- sections swapped between two members

### Units

#### `units_relabelled` -- units relabelled without conversion

* **Effect class**: `changes-analysis`
* **Material through**: `analysisChange`, `designPassFailChanged`
* **What it changes**: Changes the declared force unit or length unit and keeps every number (`/units/force` or `/units/length`).
* **Why it matters**: Every dimensional number of the file is read in the declared units, so relabelling them describes a different physical structure: lengths, sections, loads, stiffnesses and strengths all scale by powers of the unit factor. Because the unit system is consistent the model stays self-similar: the NUMBERS of the results in file units and all design ratios are unchanged -- nothing inside the file looks wrong. The error shows only against physical data stated outside the file (a span given in metres, a load in kN, a deflection limit in millimetres): every physical result is off by the unit factor.
* **Result quantities it moves**: Every physical quantity: lengths and displacements by the length factor, forces and reactions by the force factor, moments by their product. Design ratios and numbers in file units do not move.
* **Applicable when**: any model (the declared units are part of every file).

### Loads

#### `load_sign_flipped` -- load sign flipped

* **Effect class**: `changes-analysis`
* **Material through**: `analysisChange`, `designPassFailChanged`
* **What it changes**: Negates every component of one load (`/loadCases/<case>/loads/<k>/...`).
* **Why it matters**: Loads are signed along the positive axes: gravity on a model with Z up is a negative Z value. * **Effect class**: `changes-analysis`

### Second-order effects

#### `second_order_off` -- second-order effects switched off

* **Effect class**: `changes-analysis`
* **Material through**: `analysisChange`
* **What it changes**: Switches every second-order combination to first order (`/combinations/<id>/analysisType` removed or set to firstOrder; `/analysis/type` if the file sets it there).
* **Why it matters**: Under axial compression a frame that sways (P-Delta) and members that bow (P-delta) pick up additional moments and displacements that a first-order analysis does not see. Where the amplification is material the first-order results are unconservative: smaller drift, smaller column and beam moments. AISC 360-22 C1 requires second-order effects to be considered in the required strengths.
* **Result quantities it moves**: Drift and moments of the sway-resisting members (down by the amplification), design ratios, the design status (`conditional`: strength combinations analysed first order).
* **Applicable when**: the model has second-order combinations whose results differ materially from first order (measured: analysis change of at least 5 %; a change of a design ratio alone does not count).

## 7. Limits

* A curve ball changes ONE thing (one target, or one family of ends for `release_pinned_frame`,
  `release_mechanism` and `second_order_off`); combinations of curve balls are obtained by applying
  them one after the other (each record refers to the document it was applied to).
* At most `MAX_CANDIDATES` targets are measured per call; a model in which only a later candidate
  would matter is reported as not applicable for that seed.
* Materiality is measured on the combinations of the file and on the result quantities listed in
  section 2 (nodal rotations and buckling factors are not part of the metric).
* `units_relabelled` is measured in physical units. The file is self-similar under a relabelling, so
  results in file units and design ratios do not change; a task built on it must state physical data
  outside the file.
* `section_lighter` / `section_heavier` take a section of the model, or a neighbour in the
  generators' generic catalogue when the member's section is a catalogue entry; they do not invent
  sections for hand-written models whose sections are neither.
* `offset_added` uses half the overall depth (`d`, `H`, `D` or `h`) of the deepest non-parallel frame
  member at the joint, whatever its orientation.
* `constraint_made_flexible` uses a section and the most common material of the model for the
  stand-in members; they carry self weight and are design members.
* Support curve balls leave alone the DOFs that are fixed at every node (the out-of-plane restraint
  of a plane frame in 3D space).
* Design ratios, pass / fail and the design status are those of `benchfea.design`; whatever the
  design checks do at a discontinuity (a change of the governing limit state, of a section class, of
  the lateral-torsional segment where a moment changes sign) carries over into `designRatioChange`
  and `designPassFailChanged`.
* The record's verification route is an expectation derived from the model's features. Whether a
  perturbed model's reference solution is verified is decided only by running `benchfea verify` on it.
