# Format versioning

Every input file carries `"formatVersion": "MAJOR.MINOR.PATCH"` (semantic
versioning). The version describes the **file format** — the JSON Schema in
`src/benchfea/schema/` plus the semantic rules and conventions — not the
software release.

Current version: **1.0.0** (schema file `benchfea-input-1.0.schema.json`).

## Rule for changes

| change | bump | old files | old engines |
|---|---|---|---|
| A valid file would be refused, or would produce **different results** (a field removed or renamed, a meaning, unit, sign convention or default changed, a rule tightened) | **MAJOR** | must be migrated | refuse the new files |
| Purely additive: a new optional field, a new enumeration value, a new load/section/constraint type, a rule relaxed. Every valid file of the previous minor version stays valid **with identical meaning** | **MINOR** | unchanged | refuse the new files (they may use features the engine does not know) |
| No change to what is valid or what it means: descriptions, hints, documentation, clarifications | **PATCH** | unchanged | accept |

Consequences that the engine enforces:

* An engine that implements `M.m` accepts files with `formatVersion` `M.x.y`
  for every `x ≤ m` and any `y`, and refuses everything else with problem code
  `version.unsupported` (before any other validation).
* **Defaults are part of the format.** Changing a built-in default changes
  results and is therefore a MAJOR change. A file never changes meaning without
  its `formatVersion` changing.
* Unknown properties are errors, never ignored — a typo cannot silently fall
  back to a default.
* A new schema file is published for every MAJOR.MINOR
  (`benchfea-input-M.m.schema.json`); earlier schema files stay in the
  repository. The schema is generated by `benchfea/schema/build_schema.py`
  and a test keeps the committed JSON identical to the generator output.
* Conventions (`conventions` block) can only gain supported values in a MINOR
  version; an existing value never changes meaning.

## Checklist for a format change

1. Decide the bump with the table above; when in doubt it is MAJOR.
2. Update `benchfea/defaults.py` (`FORMAT_VERSION`, `SUPPORTED_MINOR`), the
   schema generator and the semantic validation; regenerate the schema.
3. Add fixtures: a valid file using the change, and invalid files for each new
   rule with the expected problems (`tests/test_validate.py`).
4. Record the change in the table below and, for a MAJOR bump, provide a
   migration note (and a converter when the change is mechanical).

## Output documents

Results and design output have their own format names and versions, following
the same rule: `benchfea-results` 1.0.0 and `benchfea-design` 1.0.0
(`benchfea/results.py`). Each output document repeats the units of the input
file and carries the "defaults used" report.
